账号服务开源选型 ​

核验日期：2026-10-20。本文基于官方文档和主仓库，记录候选方案与工程判断；本次没有安装身份服务、引入运行依赖或完成兼容性实测。最终采用前须锁定版本，再核许可、所需功能及实际升级方式。

决策：复用身份服务，保留自己的业务模型 ​

首版优先验证 一个成熟身份服务 + 现有 Node 业务 API + PostgreSQL + 对象存储。身份服务及其 Console 负责登录、身份连接和会话；OpenBot 负责租户、工作空间、Bot 类/实例、记忆、设备授权、同步和服务权益。当前单拥有者 Node API 是可复用起点，仍需增加经过验收的多用户授权层，不能直接对公众开放。

按 Search → Adopt → Adapt → Build 的顺序选择：采用标准和维护成熟的组件，薄适配已有运行服务；只自建 OpenBot 特有的业务与同步逻辑。不要同时把独立身份服务和 Supabase Auth 设为两个必须维护的账号来源。

层首版处理方式仍需 OpenBot 完成的部分
登录与会话Adopt：选一个 OIDC 身份服务及其官方 SDK/Console账号映射、设备绑定、客户端接入与撤销验收
业务 APIAdapt：复用现有 Node 路由、审计和执行边界多用户/租户范围、成员角色、凭据与后台隔离
关系数据Adopt：PostgreSQL；以事务、约束和按需行策略配合服务层授权Workspace/Bot实例/私有记忆模型和迁移
文件与备份Adopt：成熟对象存储，供应商通过适配层选择授权下载、归属、生命周期、配额和恢复测试
管理后台Adopt IdP Console；Adapt 少量业务管理页租户/设备/套餐/运行管理；避免重复造登录后台
同步与权益Build：围绕现有版本/权限模型做最小业务层增量、冲突、删除、幂等、套餐和计量

PostgreSQL采用其开源许可。对象存储可选云商托管服务或符合需求的自托管实现；本轮不指定容量、价格或承诺所有对象存储接口完全兼容。

身份服务候选 ​

优先验证 Logto OSS 的标准登录路径，Casdoor 作为微信场景和 Apache 许可优先时的替代；Keycloak 保留为企业身份需求增强时的备选。这是针对当前 Node 技术栈和初期运维规模的判断，不是已经完成的选型或性能结论。

候选已核实能力和主仓许可OpenBot 适配判断
LogtoNode.js/PostgreSQL、OIDC/OAuth、用户/组织/RBAC与Console；主仓MPL-2.0；官方有Google/GitHub及微信Web/Native连接器优先PoC / Adopt + thin adapter。生态接近现有Node服务；但OSS文档列有商业能力边界，先核后台协作、强制Console MFA、自定义UI/去品牌等所需项
Casdoor独立Go服务与数据库，用户/组织/应用/Provider管理；OAuth/OIDC与PKCE，Google/GitHub/微信接入文档；主仓Apache-2.0备选 / Adapt。通过OIDC接Node，不必同语言；优先核微信目标场景、账户绑定与管理员要求，不能把内置订阅功能视为完整OpenBot计费
Keycloak用户/会话/角色/组织与管理Console，OIDC/OAuth及PKCE，内置Google/GitHub；主仓Apache-2.0企业备选 / Reference。企业SSO需求明确时再评估其配置与运维面；微信未列为内置社交Provider，需要扩展或上游身份代理验证

官方依据：Logto主仓、Logto OSS及商业边界、连接目录；Casdoor主仓、OAuth/PKCE；Keycloak管理文档、主仓许可。

开源代码可自托管，不代表全功能永久免费或无需运维。Logto OSS未覆盖或需要商业授权的功能，应纳入预算和采用条件；若所需后台控制无法在预算内满足，保持业务侧OIDC接口，转而验证Casdoor，避免先写大量供应商专属业务逻辑。

微信登录必须按场景核验 ​

场景接入对象本轮核验结论
桌面浏览器扫码微信开放平台的网站应用Logto WeChat Web、Casdoor Web文档覆盖这类路径；仍须配置自己的应用与回调
iOS/Android原生唤起对应移动应用注册、签名/Bundle ID与微信SDKLogto Native文档明确覆盖iOS/Android；客户端回跳与账号绑定仍需真机验证
微信内网页公众号网页授权Casdoor文档中的Mobile指此场景，不能将它当作原生App SDK路径的证据

依据：Logto WeChat Web、WeChat Native、Casdoor微信Provider。跨场景的用户标识关联还取决于微信平台配置，不假定天然统一。OpenBot内部始终使用自己的稳定账号ID，不按昵称或相同邮箱自动合并。

Supabase：整套后端替代路线 ​

如果后续同时需要Auth、数据库API、Storage、Realtime与Studio，可以单独评估自托管Supabase，替代自行组合部分组件；首版仅为登录而引入整套服务并不一定更简单。Supabase主仓为Apache-2.0，部署组成仍需按实际组件分别核许可。主仓许可

官方自托管文档说明：自托管不是托管平台的完整管理服务，单项目Studio不等于多租户业务后台，升级、备份、数据库维护由部署者承担；托管备份/PITR和Management API等能力不会自动附带。选它仍需承担运维和实际容量验证。自托管范围、Docker部署组成

数据库RLS可以参与用户/租户隔离，但必须配合grants、每种读写操作策略和服务端鉴权。service_role会绕过RLS，不能发给桌面、手机、浏览器或普通Bot。RLS官方说明

Realtime提供数据库变更订阅。它不能自动完成OpenBot的离线同步，是本项目的架构判断：现有本地JSON、CAS冲突、删除传播、断线补齐、成员撤权和执行审批仍需业务协议。不能把“能订阅变更”描述为“所有端登录后自动同步全部资料”。Postgres Changes

业务后台与计费：按需要增加组件 ​

首版直接复用所选身份服务的Console，另做少量受控业务页面。后台逐渐涉及复杂CRUD、筛选和权限展示时，可适配 Refine（主仓MIT）；它提供React管理应用的数据/认证/权限接口，不能替代服务端租户校验。Refine文档、许可

计费首版先维护 plans/subscriptions/entitlements/payment_events/usage_events 和支付渠道适配器。以Stripe官方Webhook文档作为机制参考：回调需验签、去重并处理事件乱序；客户端支付成功页面不能授予服务端权益。这不代表已选择Stripe，或承诺任何地区、渠道和币种都可开通。Webhook说明

出现复杂用量计量、预付费或订阅组合后，再评估 Lago。其主平台采用AGPLv3，Cloud/Premium能力另列；采用前核实际版本、开源能力与许可要求，不能按宣传页把全部功能写为免费。它是后期候选，本轮不引入新的计费平台。Lago版本与功能边界、许可

OpenBot的免费/付费套餐、开源身份组件的商业版费用、云资源费用和模型费用是不同项目，应分别核算。

下一步验证与采用条件 ​

  1. 在隔离环境部署一个候选IdP，完成一个第三方来源→系统浏览器/PKCE S256→内部账号映射→退出/撤销的完整闭环；再扩展其余来源与手机真机。
  2. 两个账号各有个人租户，验证A不能读取B的配置、文件、索引、记忆、订阅和实时事件；团队加入/退出也不泄露旧私聊。
  3. 完成两个设备对同一实体的版本冲突、增量补齐、删除与撤权；官方登录不自动上传本机凭据或浏览器资料。
  4. 验证身份服务、业务库和文件的备份恢复及升级，确认管理员控制满足需求；记录锁定版本与第三方许可清单。
  5. 接入一个支付测试渠道，验证重复/乱序/失败/退款通知与权益到期，明确免费配额和成本上限后再发布套餐。

这些是后续实现验收条件，不是本次调研已通过的测试。产品模型与数据边界见官方账号与数据服务。
